--- title: "OLAP vs OLTP" description: "Comparing OLAP and OLTP workloads, optimization strategies, and columnar vs row storage approaches." date: 2026-05-12 board: database url: https://dingjiu1989-hue.github.io/en/database/olap-vs-oltp.html --- ## Workload Characteristics OLTP (Online Transaction Processing) and OLAP (Online Analytical Processing) serve fundamentally different purposes. ## OLTP Characteristics High-volume, short, atomic transactions: ```sql -- OLTP: small, frequent transactions BEGIN; UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 123 AND quantity > 0; INSERT INTO order_items (order_id, product_id, quantity, price) VALUES (5001, 123, 1, 29.99); INSERT INTO orders (id, customer_id, total, status) VALUES (5001, 42, 29.99, 'confirmed'); COMMIT; ``` OLTP optimizations: fast writes, small queries, high concurrency, row-based storage. ## OLAP Characteristics Large, complex, read-heavy queries: ```sql -- OLAP: large aggregation queries SELECT DATE_TRUNC('month', o.order_date) as month, c.region, p.category, COUNT(DISTINCT o.id) as order_count, SUM(oi.quantity * oi.unit_price) as revenue, AVG(oi.quantity * oi.unit_price) as avg_order_value FROM orders o JOIN customers c ON o.customer_id = c.id JOIN order_items oi ON o.id = oi.order_id JOIN products p ON oi.product_id = p.id WHERE o.order_date >= '2025-01-01' GROUP BY 1, 2, 3 ORDER BY month, revenue DESC; ``` ## Row vs Columnar Storage ```python # Row-oriented storage (OLTP) class RowStore: def __init__(self): self.rows = [] def insert_row(self, data): self.rows.append(data) # Fast insertion def get_row(self, row_id): return self.rows[row_id] # Fast single-row access # Column-oriented storage (OLAP) class ColumnStore: def __init__(self): self.columns = {} def insert_row(self, data): for col, val in data.items(): if col not in self.columns: self.columns[col] = [] self.columns[col].append(val) # Slower insertion def sum_column(self, column): return sum(self.columns[column]) # Fast aggregation ``` ## Optimization Strategies ```yaml oltp_optimizations: indexing: - b_tree_indexes_for_point_lookups - avoid_over_indexing - keep_index_fit_in_memory connection_pooling: - pgbouncer_or_proxysql - pool_size_depends_on_cores - monitor_idle_connections query_pattern: - keep_queries_simple - return_few_rows - use_cursors_for_large_results - avoid_joins_in_critical_path olap_optimizations: storage: - columnar_compression - partitioning_by_date - materialized_views execution: - vectorized_query_execution - parallel_query_processing - result_caching schema: - star_schema_design - pre_aggregated_tables - bitmap_indexes_for_low_cardinality ``` ## When to Use Which | Aspect | OLTP | OLAP | |--------|------|------| | Reads/Writes | Balanced | Mostly reads | | Query size | Small | Large | | Concurrency | High | Low | | Latency | ms | seconds-minutes | | Data freshness | Real-time | Periodic | | Typical DB | PostgreSQL, MySQL | ClickHouse, Snowflake | ## Hybrid Approach Modern databases like PostgreSQL can handle both with careful design: ```sql -- Separate OLTP and OLAP workloads -- Materialized view for analytics CREATE MATERIALIZED VIEW mv_daily_sales_analytics AS SELECT DATE_TRUNC('day', order_date) as day, product_category, SUM(amount) as total, COUNT(*) as transactions FROM orders GROUP BY 1, 2; REFRESH MATERIALIZED VIEW mv_daily_sales_analytics; ``` ## Conclusion Use OLTP databases for transactional workloads and OLAP databases for analytics. Attempting to use one for both leads to poor performance. Use CDC (Change Data Capture) to replicate from OLTP to OLAP. Consider HTAP databases like TiDB or SingleStore if you genuinely need both on the same platform.
